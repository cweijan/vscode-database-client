## Context

当前项目来自旧版 `vscode-database-client` 源码，原构建链使用 Webpack 和旧版 Vue 生态。恢复分支已经保存了 9.0.2 活动扩展的清单、资源、Webview 产物和编译后的扩展入口，但目标安装目录没有 source map，公开仓库也没有对应 9.0.2 源码。目标 bundle 中保留的源码路径标记可以作为模块清单和行为定位证据，但不能直接作为可维护源码。

本设计把目标活动 bundle 当作行为基线，把旧项目源码当作可复用的历史实现，以垂直领域切片重新实现现代源码。用户可见的命令 ID、视图 ID、配置键、文件关联和数据库连接协议是兼容边界；目录、模块边界和内部实现可以现代化。

## Modernization boundary

恢复目标是行为兼容和可维护源码，不是复制旧项目的内部目录、压缩模块边界或历史框架。只要命令、配置、消息、数据库语义、持久化状态以及页面视觉和交互保持兼容，内部就可以采用更清晰的领域模块、类型化端口/适配器和明确的生命周期管理。现代化只针对代码、依赖和构建工具链，不进行无关的页面视觉改版。

## Goals / Non-Goals

**Goals:**

- 建立可由干净 checkout 重复执行的 Vite、TypeScript、Vue 3 构建和打包流程。
- 将扩展后端、数据库能力和 Webview 变成明确的源码模块，而不是依赖单个编译 bundle。
- 用清单、bundle 路径标记、功能场景和构建产物证明 9.0.2 能力没有被遗漏。
- 保留当前活动版的 Oracle 同义词支持和其他本地修改。
- 让后续功能修改可以在源文件、类型检查和测试层完成。

**Non-Goals:**

- 不承诺恢复原作者逐字一致的 TypeScript、Vue 文件、注释或变量命名。
- 不在本变更中重新设计用户界面、改变用户数据目录或更换数据库协议。
- 不在源码尚未覆盖前删除旧源码或以压缩 bundle 作为唯一源码。
- 不为追求“现代化”而改变命令、配置、视图和连接行为。

## Decisions

### 1. 以行为证据驱动源码恢复

每个领域先建立目标清单：package manifest surface、bundle 源码路径、资源引用、消息协议和可观察行为，再编写现代源码。旧源码可以直接复用的部分先保留语义并迁移类型；只有能由目标证据验证的新增实现才进入新模块。

替代方案是直接按 bundle 的变量和包装结构生成文件。该方案速度快，但会把打包器变量、初始化函数和压缩后的导入关系带进源码，无法满足可维护性目标，因此不采用。

### 2. 采用现代 Vite + TypeScript + Vue 3 工具链

使用目标 package manifest 已体现的 Vite、TypeScript 6、Vue 3、Vue-tsc 和 ESLint 生态，补齐缺失的 Vite 配置、源码入口、类型配置和锁定文件。TypeScript 6 作为 Vue/嵌入式语言工具链仍兼容的过渡版本，暂不把 TypeScript 7 作为迁移前提。扩展后端和 Webview 采用清晰的入口与别名，不让旧 Webpack 配置继续承担新源码构建职责。

替代方案是继续修补旧 Webpack/Vue 2 链。它能较快复用旧文件，但不能承接目标 Webview 和新模块的现代依赖，也会把迁移债务继续隐藏在构建配置中。

### 3. 按垂直领域切片，而不是按文件数量迁移

迁移顺序为：构建骨架与扩展入口、公共基础设施和连接核心、数据库树/方言/Provider/命令、Webview shell 与共享协议、具体页面和数据库扩展能力、最终清理。每个切片都必须有独立的源码入口、类型检查和行为验证，完成后才进入下一片。

替代方案是先批量恢复所有 source-marker 文件再统一修复编译错误。该方案会产生难以定位的跨模块错误，且无法判断功能遗漏，因此不采用。

### 4. 保持扩展边界稳定，内部模块可以重组

扩展外部契约以目标 package.json 和活动 bundle 为准：激活事件、commands、views、settings、languages、customEditors、MCP tools、资源路径和消息类型必须保留。内部使用面向领域的服务、适配器和类型定义，避免新代码继续依赖旧版全局状态或打包器生成变量。

### 5. 编译产物只做 golden baseline

恢复分支中的 `out` 用于逐文件哈希、静态引用检查和黑盒行为对照；源码构建生成的新 `out` 必须能够独立替换它。迁移过程中保留可回退的编译基线，完成后不把基线 bundle 当作源码依赖。

### 6. 依赖可复现优先于盲目升级

以目标 package manifest 的依赖版本范围为迁移起点，生成并提交对应 lockfile；先在 Node 20 环境完成安装、类型检查和构建，再单独评估安全或兼容性升级。不得因为升级依赖而改变数据库连接或查询语义。

## Risks / Trade-offs

- [Risk] 编译 bundle 缺少原始类型和 import/export 信息 → [Mitigation] 以源码路径标记、旧源码、manifest 和运行时行为交叉验证；无法证明的代码先作为待恢复项，不伪称已完成。
- [Risk] 新旧架构长期并存导致重复实现 → [Mitigation] 每个切片标记 source owner；新模块通过适配器接入旧能力，完成垂直验证后再移除旧实现。
- [Risk] Webview chunk 能运行但无法直接还原 Vue 源码 → [Mitigation] 先固定 extension/webview 消息协议和页面验收，再按页面重建 Vue 组件和状态管理。
- [Risk] 目标依赖没有原始 lockfile → [Mitigation] 固定 Node/npm 版本、提交新 lockfile，并在干净目录重复安装构建。
- [Risk] 大批量迁移掩盖行为回归 → [Mitigation] 每个 OpenSpec task 完成即更新任务勾选并运行对应的静态/垂直检查。

## Migration Plan

1. 从当前恢复分支建立源码迁移 change，记录目标文件清单、源码 marker 清单和外部契约。
2. 搭建 Vite/TypeScript/Vue 3 骨架，先让最小扩展入口可以构建并加载。
3. 分领域迁移后端核心和 Webview，每个领域保留旧实现作为回退，完成场景验证后切换 source owner。
4. 生成 lockfile，运行类型检查、lint、构建、打包和目标功能 smoke checks。
5. 只在新源码构建产物通过等价性检查后移除旧 Webpack 配置、旧依赖和不再引用的旧源码。

回滚策略是按 commit 回退到源码迁移前的 `codex/restore-source-9.0.2` 基线；编译版恢复分支仍保留可直接使用的目标活动产物，不依赖源码迁移的中间状态。

## Open Questions

- 真实数据库连接 smoke test 是否能在本机提供 MySQL、Oracle、PostgreSQL、MongoDB 等测试实例；没有实例时使用静态 SQL/fixture 验证，并明确标注未做真实连接验证的能力。
- Webview 的视觉像素级一致性是否属于验收范围；本变更默认优先功能、消息协议和布局稳定性，不把非功能性视觉重设计混入恢复任务。
